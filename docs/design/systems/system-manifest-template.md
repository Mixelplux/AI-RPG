# <System Name> — Design Manifest

Use this template selectively; omit inapplicable detail. Keep evidence and status
explicit. Reference [shared doctrines](README.md#shared-doctrines) instead of
redefining them. A conceptual decomposition is not proof of runtime modules.
Manifests are living models, not new implementation contracts or authorization.

## Status

- Overall: Implemented / Partial / Design only
- Last materially reviewed: date and implementation baseline
- Relevant milestones: links

Classify significant capabilities as Implemented, Partial, Accepted design,
Provisional, or Deferred using the [shared vocabulary](README.md#navigation-and-status-vocabulary).

## Purpose

What responsibility this system exists to own.

## Player-facing goal

The experience or capability enabled.

## Authority

What this system may decide; identify genuine contractual boundaries.

## Explicit non-authority

What belongs elsewhere, even if currently stored or executed in shared modules.

## Governing principles

Accepted design rules and links to shared doctrines and existing decisions.

## Current model

Conceptual structure, with status labels where implementation differs.

## Resolution depth

How the Specificity Doctrine applies without changing ownership.

## State and lifecycle

What is inferred, lazy-resolved, persistent, dormant, or actively simulated;
separate intended lifecycle from existing state transitions.

## Inputs

Authoritative inputs consumed and any untrusted proposals requiring validation.

## Outputs

Truth, results, or projections supplied elsewhere.

## Relationships

Important interfaces; link the system map and label unsettled interfaces provisional.

## Player-facing projection

What may be visible versus internal; distinguish truth, perception, and knowledge.

## Current implementation

Bounded capabilities, limitations, and source/test evidence. Do not generalize
from one proving slice.

## Accepted decisions

Agreed direction, reasoning, and existing decision references.

## Provisional decisions

Working direction and evidence needed to refine it.

## Deferred capabilities

Explicit exclusions and future work; no automatic scheduling.

## Known tensions / open questions

Contradictions, older terminology, implementation gaps, and unresolved questions
distinguished from each other.

## Evidence

Relevant sprints, implementation, tests, play findings, and design conclusions.
Distinguish historical reported verification from checks performed in this review.

## Revision history

Meaningful directional changes only; date, change, and reason.
