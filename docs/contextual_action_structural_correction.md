## Root causes and correction

GameEngine.process_command offers input to contextual handling before the
investigation and legacy routes. interpret rejected every non-social occurrence
of `if` before selecting assessment. Consequently the subordinate feasibility
clause in `I want to inspect the crooked wheel and see if I can fix its fitting.`
was mistaken for a condition on commitment, despite an inspection objective.

The interpreter now recognizes an epistemic ability clause within a bounded
assessment objective. An inspection followed by `see/check if I can/could`, or
the corresponding `whether` clause, requests an assessment. It yields the
existing observations and supported approaches with no method authorization,
preparation, cooperation, random draw, elapsed time or material outcome.
Inspection and repair never execute together. The assessment retires any
previous pending proposal, so a subsequent `confirm` cannot authorize it.

A condition on a commitment remains rejected. `Fix the fitting if Tessa agrees`,
`confirm if I can fix the wheel`, `only if`, and a second conditional clause
cannot authorize execution. Direct adjustment creates a disclosed proposal;
`confirm`, `yes, do it`, or an equivalent adjustment imperative can authorize
that single pending method. Existing restrictions, fresh context/disclosure
checks, atomic publication and outcome replay remain unchanged.

The Market declaration also omitted `fitting` from its visible feature aliases,
although the assessment and adjustment method name that feature. Adding that
authored reference allows direct fitting objectives to resolve through the
existing target binder. No command-specific branch, new method, generalized
language system, presentation change or persistence field was introduced.

## Cooperation transition and authority review

`Now let's move the cart out of the passage` selects the existing
coordinated_shift method and discloses its one-hour uncertain attempt. The
proposal makes no agreement or material change. Upon confirmation, assess checks
the actual helper location, authored refusal conditions and any persisted
refusal. Accepted routine preparation includes requesting and coordinating that
helper; only then does material_preparation record willingness, bracing and
authorization in the copied candidate. No preceding separate offer is required.

Time advancement runs in that candidate. The method is assessed again before
the engine-owned draw and material outcome. Existing material history validation
independently verifies the helper's historical presence, refusal policy,
preparation, authorization, time source and exact consequences. World/scene
publication is atomic; construction failure leaves world, scene and pending
authorization unchanged. This cooperation behavior is adjudicated, so it is
retained. The production CLI refusal and absent-helper cases produce no
preparation, movement, draw or elapsed cost. A failed fitting attempt followed by
an explicit cooperation request produces an authoritative refusal, without help.

Classification remains an unsaved input boundary, not simulation authority.
All material changes continue through the existing candidate/time/history/
validation/publication pathway. Save version remains 1, with no migration.
